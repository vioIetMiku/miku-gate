# 自动验证 VPN Gate 服务器身份并绑定指纹

> 开发中的真实身份流程：标准TLS证书校验不等于VPN隧道或住宅属性验证。手动名称模式继续保留，但不再默认让用户猜证书CN。完整功能范围见FINAL_FEATURES与DELIVERY_PLAN，已有Release不替换。

## 为什么不能只使用列表名称

本次从官方HTTPS列表选取两个公开TCP端点，对其官方`vpn数字.opengw.net`域名执行系统CA验证的TLS握手，均成功。其SAN覆盖`*.opengw.net`，但CN是`opengw.net`，不是每条列表里的`vpn数字`。OpenVPN的`verify-x509-name ... name`检查CN，不能直接照抄列表名称。

两个节点还返回同一叶证书指纹，说明该公共基础设施可能共享证书。身份校验可以限制连接到指定证书/官方名称，不能证明节点独享、住宅或运营者信誉；界面明确保留这一限制。

## 默认操作流程

1. 同步官方节点，选择要使用的候选。
2. 点击“验证官方TLS身份”：只向该候选的一个数字IP/端口发一次标准TLS握手。TCP使用OpenVPN配置中的端口；UDP候选检查固定443。不遍历端口，不发送VPN客户端身份或私钥。
3. TLS至少1.2，使用系统根CA及官方来源主机名的SAN校验；通过后提取合法CN、叶证书SHA-256及有效期。
4. 服务端短暂缓存5分钟，按节点ID、IP、配置快照哈希绑定。浏览器仅提交`use_verified_identity:true`，不能提交“已验证”的证书结果来欺骗后端。实际请求限制串行、最少间隔3秒、最多缓存32条。
5. 用户确认算法兼容/替换出口后，保存加密的配置快照、CN和证书指纹。OpenVPN仍做服务器角色、CA、名称、有效期检查，额外固定叶证书指纹。证书轮换后需重新核验，不自动接受不同证书。
6. 只有后续VPN握手、worker DNS/业务TLS和实际出口核验成功，才开放认证代理入口。

如果节点没有可验证的TLS监听或证书校验失败，会明确失败，不改用insecure选项或端口扫描。高级用户可选择已有独立来源的手动名称模式；该模式不会冒充自动验证或自动附加指纹。

## 数据与升级

新增`POST /api/nodes/{id}/identity`，需要管理员会话与CSRF。返回的是公开证书元数据、时间、来源和静态快照指纹，没有证书私钥或OpenVPN配置正文。

数据库schema升为5，防止旧程序忽略新保存的证书指纹。升级前停止服务、备份整个数据目录和配套`.key`；回滚不能只换旧二进制。自动检查记录代表保存时的观察，不是当前实时在线状态。

## 测试及实际范围

单元/私有TLS测试覆盖：官方名称映射、系统CA/SAN验证、错误名称拒绝、固定数字端点、私网/陈旧/非官方来源拒绝、指纹规范化、跨节点/配置/时间的缓存拒绝、认证/CSRF/频率限制、加密快照和指纹持久化。

受控原生OpenVPN旅程新增正确指纹及错误指纹负向对照，需要实际运行后才算通过。自动身份流程的公共TLS观察不等于已完成公共VPN连接；`scripts/vps-vpngate-live.py`提供明确同意后最多两节点的正式CLI验收，独立记录成功或失败，不用测试意图替代结果。
