# v0.2.4 连接策略与调研

本次在 v0.2.3 的 Go + OpenVPN + Linux netns 架构上修改，继续使用原来的入口、身份验证、国家校验与订阅流程。没有引入新核心或第三方运行脚本。

## 创建出口

普通创建和一键配置共用 `runExitRace`。国家配额来自当前请求，普通创建不受日本 / 韩国 / 美国预设限制。

| 请求 | 候选并发上限 | 最终保留 |
| --- | --- | --- |
| 日本 3 个，至少 9 个不同候选 | 9 | 最先验证成功的 3 个 |
| 韩国 3 个，至少 9 个不同候选 | 9 | 最先验证成功的 3 个 |
| 任意国家 3 个，只有 3 个候选 | 3 | 最多 3 个 |
| 日本 3 个、韩国 3 个 | 各 9，合计 18 | 各 3 |
| 槽位不足以容纳三倍竞发 | 在剩余槽位内分配，先保障各国家目标 | 不超过目标和实际容量 |

同 hostname / IP 的候选与已有出口不会重复连接。候选通过 OpenVPN、真实出口 IP、国家与入口就绪检查后才成为可见出口，立即可复制和订阅，不等待本批其余出口。某国达标后停止其多余连接；清理等工作器退出再释放槽位，防止旧工作器误拆新命名空间。候选不足但存在目标时会继续刷新来源并补齐，可通过任务里的「停止补齐」取消，成功出口保留。「全部停止」也会取消后台创建任务。未完成创建任务不跨服务重启恢复。

## 保持当前节点

- OpenVPN 在无出站数据时每 10 秒发送保活；45 秒没有收到远端数据后尝试软恢复。使用 `persist-tun` 和 `persist-key`，保留虚拟接口和密钥，减少重建成本。客户端会过滤远端推送的 ping / inactive 参数，并去除导入配置中冲突的本地超时；证书、密钥与加密参数保持原样。
- 连接重试间隔从 1 秒开始，最高 8 秒；单轮允许重试当前远端 2 次。竞发候选的连接超时为 8 秒、等待接口最多 28 秒、全流程最多 50 秒，达到配额即可更早取消。成功候选不再保留原先 22 秒的激进 TLS 握手窗口，后续恢复 / 协商沿用 OpenVPN 默认值。
- 每 10 秒安排有界健康检测。依次尝试 ipify、Ping0 和 AWS Check IP；任意一个返回当前出口 IP 即成功，所有请求仍绑定本条 netns 的 `tun0`，保留 TLS 校验。
- 普通探测失败须至少 3 次，且从首次失败起持续至少 75 秒才触发管理器重建。这个窗口给 45 秒软恢复留下约 30 秒额外余量；在通常 10 秒采样节奏下，实际会在更晚的下一次失败结果确认，不是精确 75 秒定时器。任何一次成功都会清空失败窗口。
- 有效响应明确返回错误出口 IP 时不等待普通宽限。代次和端点均须匹配，旧连接的结果不能触发新连接重连。
- 确需重建时优先尝试原节点；确切 TCP 预检失败时可让同国家备选领先。仅延迟更低、ASN 更接近不会挤掉仍可达的原节点。不保证真实断网时已建立的 TCP 会话完全无损。
- 自建核心对照运行配置和引用证书的指纹；内容相同且核心进程仍运行时跳过重复重启。原节点恢复后的重复对账不会再中断其他出口，实际配置变化、同路径证书续期和核心退出仍会触发重启。

75 秒是本项目选定的恢复取舍，不是下列标准强制的数值。它会延后确认部分真正故障；相应地减少探测网站不可用或短暂网络抖动带来的换节点。

## 网上调研与采用范围

| 官方来源 | 可靠方法 | 本次采用 |
| --- | --- | --- |
| [RFC 8305 §5](https://www.rfc-editor.org/rfc/rfc8305.html#section-5) | 多个连接尝试竞争，成功后取消其余尝试 | 复用已有竞发与取消机制，推广到普通创建。RFC 原本面向双栈地址且建议错开启动；本项目按用户要求对不同 VPN 端点同时竞发，并非完整实现 Happy Eyeballs。 |
| [OpenVPN 2.6 官方手册](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html) | `ping` / `ping-restart`、`persist-tun` / `persist-key`、有上限的 `connect-retry`、按顺序匹配的 `pull-filter` | 配置原节点软恢复、统一本地保活策略；管理器在持续故障确认后才重建。 |
| [sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/) | 延迟容差、可配置是否中断已有入站连接 | 借鉴减少换线和保留连接的思路；没有向服务端硬塞客户端 URLTest，也未复制项目代码。 |
| [Mihomo URL-Test](https://wiki.metacubex.one/en/config/proxy-groups/url-test/) | 节点切换容差 | 借鉴避免相近延迟导致频繁切换的原则；本项目健康检查不因延迟差异主动换节点。 |

## 验证

新增回归覆盖普通国家的 9 路 / 3 路竞发、首个结果即时展示、剩余候选清理、订阅及恢复状态隔离、取消单任务与全部任务、重复端点统计、瞬时故障恢复、持续故障阈值、第三探测来源、旧代次隔离、原节点优先和内联密钥保留。沿用已有快速配置、入口与持久化回归，并执行 Go race / vet、安装器测试和页面 DOM 交互测试；发布构建从源码重编译 amd64 / arm64，重新生成内部清单和 SHA256。

此工作环境没有 `/dev/net/tun` 和可用的 netns 权限，相关环境依赖用例会跳过。离线回归和交叉编译不代表已完成真实 VPN Gate 节点、客户端端到端速度或数小时掉线率实测；需在目标 VPS 验收。公共志愿节点本身的下线、拥塞和服务器主动断开仍可能导致中断。
